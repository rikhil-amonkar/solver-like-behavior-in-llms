IMPORTANT: Avoid solver-like reasoning patterns. Solver-like behavior occurs when the reasoning performs the problem instance's actual computation in natural language—substituting given values into arithmetic or deriving intermediate or final results in prose—before any code is written. This defeats the purpose of formalization.

Example problem: "Weng earns $12 an hour for babysitting. Yesterday, she just did 50 minutes of babysitting. How much did she earn?"

Solver-like reasoning (avoid this): Weng earns $12 per hour, and babysat for 50 minutes. Since there are 60 minutes in an hour, her per-minute rate is 12/60 = $0.2 per minute. For 50 minutes, she earned 50 * 0.2 = $10. So the answer is $10.

Sound reasoning (correct approach): This problem involves converting an hourly wage into a per-minute rate, then scaling it by the number of minutes worked. I'll define variables for the hourly rate (12) and minutes worked (50). The formalization involves: (1) computing the per-minute rate by dividing the hourly rate by 60, and (2) multiplying the per-minute rate by minutes worked to get total earnings. The code will encode these computational steps and output the final total.

The key difference: In solver-like reasoning, you perform arithmetic during reasoning (computing 12/60 = 0.2, then 50 * 0.2 = 10), arriving at the specific numerical answer before any code exists. In sound reasoning, you identify the problem's structure (rate conversion, scaling), define the relevant variables and their relationships, and describe the computational process without performing the actual calculations. Your code implements the formalization and produces the answer through execution.

Do not compute intermediate values or final answers during reasoning. Instead, reason about the formalization by naming variables and constraints, outline the steps a program would take, and let your code perform all calculations through proper algorithmic implementation.
